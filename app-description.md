# Дашборд сделок CRM — описание приложения VibeCode

Сервисный дашборд по сделкам основной воронки (категория 0) портала Битрикс24.

## Инстанс

- Поддомен (Black Hole): `https://app-c52c89249e3e.vibecode.bitrix24.tech`
- Сервер (id): `dd6aa2e1-2e92-4463-98b0-a5d28185f7da`, имя `crm-deal-dashboard`, kind `STANDALONE`, mode `BLACKHOLE`
- accessPolicy: `OWNER_ONLY`
- Портал: `b24-yfbqyg.bitrix24.ru`
- Последняя версия исходников: `v4` (sha256 `96caa2ac89dfe69d6ec7e93c4cb064b7aef705c582b46282701124cac414cc34`); актуальный код — в архиве/deploy.zip к этой сдаче.

## Функции

- `GET /` — статическая страница дашборда (воронка, KPI, последние сделки).
- `GET /health` — открытый health-check для платформы (единственный маршрут вне `/api`).
- `GET /api/meta` — стадии основной воронки из `/v1/statuses` (entityId `DEAL_STAGE`), кэш 5 минут.
- `GET /api/data?from=...&to=...` — сводка и KPI по периоду; последние сделки (10, с `select`).
- `GET /api/me` — прокси к `GET /v1/me`: `type`, `scopes`, `accessMode`, портал, владелец.

## Агрегаты и KPI (по замечаниям раунда)

- Сводка и KPI строятся только из `POST /v1/deals/aggregate` (сумма `amount`, `groupBy: stageId`, фильтр по `categoryId` и периоду).
- `POST /v1/deals/search` используется только для блока «Последние сделки»: `limit 10`, `select` (`id, title, amount, stageId, categoryId, currencyId, assignedById, createdAt`), сортировка `createdAt desc`.
- KPI «Выиграно» — строго по `stageSemanticId === 'S'`.
- Открытые деньги — стадии, где `stageSemanticId` не `S` и не `F`.
- Средний чек = сумма выигранных / количество выигранных; конверсия = выигранных / всех сделок воронки.

## Валюты: итоги разделены, смешивания нет

Денежные итоги **никогда не складываются между валютами**:

- `POST /v1/currencies/search` даёт список валют портала (агрегат по `currencyId` платформой не поддерживается — проверено, `400`);
- `POST /v1/deals/aggregate` гоняется отдельно по каждой валюте (`filter.currencyId`, `groupBy: stageId`) — сводка и KPI строятся только из агрегатов, `search` по-прежнему только для 10 последних сделок;
- `/api/data` отдаёт `stages[].amounts` (суммы по каждой валюте) и `summary.perCurrency` (`openSum`, `wonSum`, `avgCheck` на валюту); количество сделок — валютно-нейтрально;
- в шапке дашборда — фильтр по валюте (`/api/meta` отдаёт список валют с флагом базовой, `/api/data?currency=XXX` считает только выбранную; по умолчанию — базовая валюта портала);
- KPI — всегда ровно 4 доски (Открыто / Выиграно / Средний чек / Конверсия), суммы и валюта в них следуют за выбранной в фильтре валютой;
- фронт рисует KPI по валютам отдельно (каждая сумма — с символом валюты), воронка при нескольких валютах показывает количество и суммы по валютам по строкам.

Если на портале одна валюта — вид как раньше (расчёт корректен, смешивать нечего), в футере остаётся допущение «портал ведёт сделки в одной валюте».

## Авторизация и гейт доступа

Сервисная модель: личный ключ `vibe_api_…` в заголовке `X-Api-Key` при вызовах `/v1/*`; данные читаются как владелец ключа. Поэтому политика сервера — `OWNER_ONLY` (только владелец ключа; сотрудники портала сделки владельца не видят).

Гейт на маршрутах `/api/*` проверяет опознанность посетителя по заголовку **`X-Vibe-User-Id`** (его добавляет шлюз Black Hole для идентифицированных пользователей). Без него — `401`. `X-Vibe-Authorization` для гейта **не** используется: этот заголовок может законно отсутствовать у гостевых ссылок и у пользователей без токена приложения, даже когда личность известна (рекомендация /docs/infra/app-runtime). Для вызовов `/v1/*` апстрим использует `X-Api-Key` с ключом из `VIBE_API_KEY`.

## Скоупы и обоснование

Рантайм-ключ в `ENV` приложения узкий — только `crm`. Проверено `GET /v1/me`: набор скоупов — `crm` (без `vibe:*`).

| Скоуп | Использование в приложении |
|---|---|
| `crm` | Чтение сделок (`/v1/deals/aggregate`, `/v1/deals/search`, `/v1/statuses`) — единственный нужный дашборду; итого рантайм-ключ имеет только его. |
| `user` / владелец | Отдельного скоупа `user` в наборе нет. Владелец определяется через `GET /v1/me` (поле `owner`) — сервисное приложение не привязано к пользовательской сессии Битрикс24. |
| `vibe:infra` | На рантайм-ключе отсутствует. Вынесен на отдельный деплой-ключ, чтобы работающее приложение не могло управлять серверами. |

Разделение ключей:
- **рантайм-ключ** (в `ENV` приложения): `vibe_api_YoGll…`, только `crm`;
- **деплой-ключ** (для заливки/управления): `vibe_api_mFI0…`, только `vibe:infra`.

## Тип ключа

- **Рантайм-ключ** `vibe_api_YoGll…` — личный API-ключ (`type: personal`), скоупы: только `crm`.
- **Деплой-ключ** `vibe_api_mFI0…` — личный API-ключ, скоупы: `vibe:infra` (служит только для заливки/управления, в ENV приложения не попадает).
- Портал: `b24-yfbqyg.bitrix24.ru` (оба ключа).
- Ключ хранится только в переменной окружения `VIBE_API_KEY` на сервере; в клиент и кодовую базу не попадает.

## Ограничения

- Режим `READONLY`: пишущие вызовы блокируются (`WRITE_BLOCKED_READONLY_KEY`).
- Rate limit на ключ: `10 req/s`; лимит по IP `60 req/s`.
- На `429` — retry с backoff: до 5 попыток, экспоненциальная пауза с учётом `Retry-After`, не дольше 60 с.
- Кэш стадий воронки — 5 минут.
- Только основная воронка (категория `0`).
- Одна валюта (допущение, см. выше).
- Политика `OWNER_ONLY`: посетитель-владелец видит данные владельца; прочим — отказ.

## Обработка ошибок (по замечаниям)

- Каждый обработчик `/api/*` обёрнут в `try/catch`.
- `friendlyError()` даёт понятные сообщения: `401` — неверный/отсутствующий ключ или неопознанный пользователь; `403` — мало скоупов; `422` — агрегация отклонена порталом (превышен бюджет стоимости, сузьте период); `502` — шлюз/API недоступен; `504` — превышен лимит ожидания (25 с).
- Backoff на `429` — см. «Ограничения».
- На каждый запрос к Vibe API стоит таймаут 25 с (AbortController): вместо бесконечного висения — быстрый `504` с понятным текстом.
- Агрегаты по валютам выполняются **строго последовательно**: параллельный залп упирается в лимит стоимости портала (`422 AGGREGATION_LIMIT_EXCEEDED`); справочник валют кэшируется 30 минут.
